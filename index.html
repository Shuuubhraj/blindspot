About the tool

Why Blindspot exists

Every Android security tester knows the problem. The fast way to check an APK is to upload it to a cloud scanner, but that means handing a client's app, sometimes unreleased, sometimes full of secrets, to a stranger's server. The safe way is manual review, but reading thousands of lines of decompiled code by hand is slow and easy to get wrong.

Blindspot is the third option: a full security assessment platform that runs entirely on your own machine. The name is the point. Every scanner has blind spots: patterns it does not check, code it skips, findings it reports once and never verifies. Blindspot attacks those blind spots three ways: a large hand-written rule set, a second independent scanning engine, and a local AI reviewer that reads the code the rules cannot judge. Where the engines agree, confidence goes up. Where only one engine sees something, it is labelled honestly as unverified instead of being dressed up as fact.

🔒

Private by architecture

There is no cloud component at all. The APK, the decompiled source, the findings and even the AI model stay on the local machine. It works fully offline once set up, which makes it safe for client apps and internal builds.

🎯

Evidence, never guesses

Every finding points to a real file and a real line number in the decompiled code, with the exact snippet attached. If a location cannot be verified, the finding says so. Line numbers are never invented.

📋

Reports a client can read

Each scan produces a full HTML, PDF or JSON report mapped to the OWASP Mobile Top 10, MASVS and CWE, with severity, confidence and remediation for every issue.

The local promise

Technology

What it is built with

Two languages do almost all the work: Python for the analysis backend and TypeScript for the web console. Everything else is a specialised tool plugged into the pipeline.

Backend: Python 3.12

  • FastAPI + Uvicorn for the REST API and live progress streaming
  • SQLAlchemy 2 + SQLite for scan history and findings storage
  • Pydantic 2 for request and configuration validation
  • Typer for the blindspot command line interface
  • ReportLab + Jinja2 to generate the PDF and HTML reports
  • pytest test suite: 542 tests (524 unit + 18 integration), all green

Frontend: React + TypeScript

  • React 18 + TypeScript, built with Vite
  • Tailwind CSS for the console styling, light and dark modes
  • Live scan dashboard fed by Server-Sent Events, so you watch each pipeline stage happen in real time
  • The built frontend is served by the FastAPI backend itself, so the whole tool is one process on localhost:8000

Analysis tools it drives

  • JADX 1.5.6 decompiles the DEX bytecode back to readable Java source
  • apktool 3.0.3 decodes resources, Smali and the manifest
  • MobSFScan runs as a second, independent rule engine
  • androguard (optional) enriches APK metadata
  • A custom binary XML parser written for Blindspot reads the manifest directly, so metadata works even before decompilation

AI: fully local

  • Ollama serves the model on localhost:11434
  • Model: qwen2.5-coder:7b, a code-specialised open model, about 4.7 GB
  • The backend talks to Ollama over plain HTTP with httpx; no API keys, no cloud calls, no cost per scan
  • If Ollama is not running, scans still work: the AI stages simply report themselves as unavailable
Under the hood

How an APK gets tested: the 9-stage pipeline

When you upload an APK, it moves through nine stages in a fixed order. Each stage streams live progress to the dashboard, a scan can be cancelled at any point, and if a scan fails or is cancelled its workspace is cleaned up automatically. Here is exactly what happens at each step.

1

Validate Input safety

The uploaded file is checked before anything touches it: is it really an APK (a ZIP with an Android structure), is it within size limits, is the archive intact? Its SHA-256 fingerprint is calculated here, which is the identity printed on every report.

2

Extract Isolated workspace

The APK is unpacked into its own private workspace folder: the DEX files, resources, native libraries (.so files), assets and the binary manifest. Every scan gets an isolated workspace, so scans never contaminate each other.

3

Metadata Own AXML parser

The manifest inside an APK is binary XML, not readable text. Blindspot parses it with its own binary XML (AXML) decoder written for this project: package name, app label, version, min and target SDK, the full permission list, exported activities, services, receivers and providers, and flags like debuggable, allowBackup and cleartext traffic. This structured manifest is what the manifest rules and several other stages reason about.

4

Decompile JADX + apktool

Two decompilers run in parallel. JADX turns the DEX bytecode back into Java source code that a human (and the AI) can read. apktool decodes the resources, the layout XML and the manifest into text form and disassembles to Smali. If one tool is missing the pipeline degrades gracefully and says so, instead of crashing.

5

External scanners Engine 2

MobSFScan, a well known open source mobile scanner, runs over the decompiled source with its own independent rule set. It is the second opinion: it knows nothing about Blindspot's rules, which is exactly what makes agreement between them meaningful later. Its rule set is vendored into the repo so it works offline.

6

Blindspot rules Engine 1 · 200 checks

Now the core of the tool runs: all 200 hand-written detection rules execute against the manifest, the Java source, the resources and the native libraries. Each rule answers with one of a fixed set of verdicts: finding, pass, needs review, not applicable or error, and every finding carries evidence with the real file path and line number.

7

AI review Engine 3 · local LLM

The local AI model reads the most security-sensitive parts of the code and hunts for issues the patterns cannot express: business logic flaws, broken access control, unsafe data flows. Every claim it makes is machine-verified before it is accepted. This stage is optional per scan and detailed in its own section below.

8

Normalize Cross-check

Findings from all three engines are merged. Duplicates pointing at the same file and line collapse into one finding that keeps the full list of which engines reported it (its provenance). When two different engines independently agree on the same location, the finding's confidence is automatically raised one level, with the reason written into the finding itself.

9

Finalize Persist + report

The scan, its findings and the engine statistics are saved to the local SQLite database, the scan appears in the history, and the HTML, PDF and JSON reports become available for download.

APK upload→ Validate→ Extract→ Metadata→ Decompile→ MobSFScan→ 200 rules→ AI review→ Cross-check→ Reports
Engine 1

The 200 checks, by category

The rules are the meal; everything else is support. Each rule is a small, focused Python class with one job, its own positive and negative unit tests, and mappings to the OWASP Mobile Top 10, MASVS and CWE. A rule must cite real evidence at a real line number or it does not fire.

35BS-N01 to N35

Network

Cleartext HTTP, weak TLS, trust-all certificate managers, broken hostname verification, missing certificate pinning, insecure WebSockets, hardcoded proxies and IPs, sensitive data in URL query strings.

30BS-W01 to W30

WebView

JavaScript bridges exposed to remote content, file access from web pages, universal access from file URLs, mixed content, SSL errors silently proceeded past, JavaScript enabled on exported activities.

25BS-S01 to S25

Storage and privacy

Secrets in SharedPreferences, world-readable files, sensitive data on external storage, clipboard and log leakage, Auto Backup with no exclusion rules, Keystore keys with randomized encryption disabled.

20BS-M01 to M20

Manifest

Debuggable builds, exported components without permissions, dangerous permissions, backup flags, deep link schemes, task affinity and strandHogg-style risks, min SDK problems.

20BS-P01 to P20

Platform and IPC

Intent injection, pending intent mutability, broadcast theft, content provider exposure, path traversal in providers, root and tamper handling, insecure IPC patterns.

20BS-X01 to X20

Hardcoded secrets

AWS, Google, Stripe, Slack, GitHub, Firebase, Twilio and SendGrid keys, JWTs, PEM private keys, keystore passwords, OAuth client secrets, credentials baked into URLs, secrets in manifest meta-data and Gradle files.

20BS-D01 to D20

Supply chain and SDKs

Advertising, analytics, crash reporting and payment SDK fingerprinting, known vulnerable library versions, obfuscation and packer detection, Flutter, React Native, Cordova, Unity and Xamarin detection, tracker census.

15BS-C01 to C15

Cryptography

DES, ECB mode, static IVs, MD5 and SHA1 for security, weak random number generators, hardcoded encryption keys, custom crypto implementations.

15BS-A01 to A15

Authentication

Biometrics without a CryptoObject, OAuth implicit flow, tokens passed in URLs, hardcoded test accounts, lockscreen fallbacks, broken session handling.

Why hand-written rules instead of only using an existing scanner?

Existing scanners are good, but their checks are generic and their misses are silent. Writing the rules myself meant every check could be tuned for accuracy, given a plain-English rationale and remediation, and tested against both a vulnerable and a clean code sample. It also means the tool's coverage is fully known: 200 named checks, each one auditable in the source.

Verification

Three engines, cross-checked

A single scanner reporting a bug is a claim. Two independent tools reporting the same bug at the same line is evidence. Blindspot is built around that difference.

🧭

Engine 1: Blindspot rules

The 200 hand-written checks. Deterministic, fast, explainable. This engine does the bulk of the work in every scan.

🔍

Engine 2: MobSFScan

An established third-party scanner with a completely separate rule set and authors. It has never seen Blindspot's rules, so its agreement is independent.

🤖

Engine 3: the AI reviewer

A local language model that reads code semantically. Slow and probabilistic, so it is used where judgement is needed, and everything it claims is verified.

  • Exact-location merge: if two engines flag the same file and the same line, the findings merge into one. Nothing is double counted.
  • Provenance is kept: the merged finding records every engine that reported it, so you can always see who said what.
  • Confidence bump: when a genuinely different engine corroborates a finding at the same location, its confidence rises one level (for example medium to high) and the reason is written into the finding's confidence rationale.
  • Honest single-source findings: if only one engine sees an issue, it stays at its original confidence. The tool never inflates a lone claim.
Engine 3

The AI reviewer: how it actually works

The AI is a local large language model (qwen2.5-coder:7b, a code-specialised model) served by Ollama on the same machine. It never replaces the rules. It does the roughly 5 percent of the work that patterns cannot: reading code for meaning.

Step 1: Picking what to read

Reading a whole decompiled app would take hours and waste the model's attention. Instead, Blindspot scores every source file with weighted patterns (authentication, crypto, network, storage, WebView and token handling score high), excludes third-party library code, prioritises the app's own package, and within those files extracts targeted snippets: merged windows of about 35 lines around each suspicious region. Snippet mode is 3 to 4 times faster than whole-file review and gives the model sharper focus.

Step 2: Asking, one unit at a time

Each file or snippet group gets its own prompt and its own timeout (300 seconds), so one slow file can never kill the whole review. The prompt demands a strict JSON answer: issue, severity, file, line numbers and the exact code snippet as proof. Output length is capped (about 3000 tokens) and the context window is set to 8192 tokens, which keeps a 7B model on a normal laptop CPU practical.

Step 3: Verifying every claim

This is the part that makes the AI trustworthy. Before any AI finding is accepted, the backend checks it against the real code: does the file exist in the workspace, do the line numbers fall in range, and does the quoted snippet match the real code word for word? Findings that pass are labelled ai-evidence-supported. Findings that fail the check are still stored, but honestly labelled ai-unverified.

Step 4: Corroborate or stand alone

If the AI independently flags the same code a rule already found (within 3 lines), the finding is marked ai-corroborated and its confidence reflects the agreement. If the AI finds something no rule caught, it is stored as an AI-sourced finding with its own label. It is never silently promoted to look like a rule finding.

  • Hallucination controls: verbatim snippet verification, line range checks, structured JSON validation, and output sanitisation (stray formatting and invented identifiers are stripped on ingest).
  • The AI is advisory: it can add findings and raise confidence. It cannot delete a rule finding or lower a severity.
  • Fully optional: AI review is a per-scan toggle with a model name field. No Ollama, no problem: the rest of the pipeline is unaffected.
  • Scan-level summary: every scan records which model ran, how many files and snippets it reviewed, and how many of its proposals were accepted versus rejected by verification.
On-demand AI

The AI Verify and AI Fix buttons

Inside the findings explorer, every single finding has two AI buttons. They run the local model on demand (180 second timeout), only when you ask, so they cost nothing during the scan itself.

✓ AI Verify: "is this real?"

The model is shown the finding and the actual code around it, and must return a verdict with reasoning. The verdict is saved onto the finding itself, so it survives reloads and appears in the interface as a pill:

true positive the issue is real   false positive the code is actually safe   uncertain needs a human call

A true-positive verdict marks the finding ai-corroborated; a false-positive verdict marks it ai-disputed. The original rule finding is never edited or hidden either way. The human stays the judge.

✦ AI Fix: "show me the patch"

The model writes a corrected version of the exact vulnerable snippet, with a short explanation of what changed and any caveats (for example, a minimum SDK requirement). It appears in a code block with a one-click Copy fix button.

The fix is stored in the finding's provenance alongside the model name, and it never overwrites the rule's own remediation guidance. You get both: the curated advice and the model-written patch.

Why on-demand instead of automatic?

A 7B model on a laptop CPU takes real time per call. Running it on all 30 findings of a scan automatically would make triage slower, not faster. Buttons put the cost exactly where the value is: the findings you are actually unsure about.

Output

Reports and data

HTML report

A self-contained, shareable report: cover with app name, package, version, SDK levels, file size and SHA-256, an executive summary, a severity breakdown, an OWASP Mobile Top 10 coverage table, a dedicated AI review section and one full section per finding with evidence, rationale and remediation.

PDF report

The same content rendered with ReportLab, one finding per page, built for sending to clients and attaching to assessment deliverables. Pure Python generation, so it works on any machine with no extra system libraries.

JSON export

The complete machine-readable scan: every finding with engine provenance, confidence history and AI verdicts, ready to feed into other tooling or a dashboard.

  • Storage: everything lives in one local folder (backend/blindspot/data): a SQLite database plus per-scan workspaces and uploads. Backing up the tool is copying one folder.
  • Interfaces: the web console, the REST API, and the blindspot CLI (Typer), which can run scans and start the server from the terminal.
  • Quality bar: 542 automated tests (524 unit + 18 integration) cover the rules, the manifest parser, the AI selection and verification logic, the cross-engine merge and the API endpoints.

FAQ

Frequently asked questions

Is Blindspot free?
Yes. Blindspot is open source and runs on your own machine. There are no subscriptions and no per-scan charges, and there is No AI Cost either, because the AI model also runs locally on your hardware.
Does it need the internet?
Only for the one-time setup, to download the tools and the AI model. After that, Blindspot works Without Internet, fully offline.
Is my APK uploaded anywhere?
Never. There are No Cloud Services involved at any stage. The APK, the decompiled code, the findings and the reports stay on your computer.
What do I need to run it?
A Windows, Linux or macOS machine with Python 3.12 and Java, plus JADX and apktool for decompiling. Ollama is optional and only needed for the AI features. The GitHub README has step-by-step setup instructions.
Which apps can it scan?
Any Android APK. Blindspot performs static analysis, so the app itself is never run. Heavily obfuscated apps still scan, though code readability and some checks may be reduced.
How is it different from MobSF?
MobSFScan is actually one of Blindspot's three engines. On top of it, Blindspot adds its own 200 checks, cross-verifies findings between independent engines to raise confidence, and adds a local AI reviewer with AI Verify and AI Fix, all in a tool built to run fully on-device.
Can it scan iOS apps?
No. Blindspot is built for Android APKs only.
